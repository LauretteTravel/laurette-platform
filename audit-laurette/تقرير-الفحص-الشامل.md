| البند | القيمة |
|---|---|
| **التاريخ** | الجمعة 13 نوفمبر 2026 |
| **المشروع** | منصة لوريت — Node.js + SQLite (node:sqlite)، واجهة عربية RTL |
| **محاور الفحص** | فحص الخلفية (Backend)، فحص قاعدة البيانات (SQLite)، اختبار إقلاع حي (Runtime Smoke) |

**منهجية النقل:** نُقلت تفاصيل كل ملاحظة (المشكلة والسبب والدليل والإصلاح) كاملةً من ملفات JSON الثلاثة أعلاه بلا اختصار، ونُقلت ملاحظات المدقق في التحقق المستقل حرفيًا كما وردت في السجل (يظهر بعضها مقطوعًا عند نهايته في السجل نفسه). أثناء إعداد هذا التقرير أُجريت قراءة مباشرة لأسطر المصدر المذكورة في كل ملاحظة (`lib/*.js` و`lib/views/*` بقارئ الملفات، و`server.js` و`render.yaml` عبر PowerShell `Get-Content` لأنهما hardlinks يرفضهما القارئ) فتطابقت المقتطفات والأرقام مع سجل الفاحصين والمدقق، وأُعيد تنفيذ فحص قرصي واحد (جرد `data/` + SHA256) توثيقه في الملاحظة SM-2. كل مقتطف كود في هذا التقرير إما منقول حرفيًا من ملف النتائج أو مقروء مباشرة من الملف المصدر، ويُشار إلى مصدره صراحة.

## 1) الملخص التنفيذي

1. أُجري الفحص على ثلاثة محاور (الخلفية، قاعدة البيانات، الإقلاع الحي) وأسفر عن **30 ملاحظة كلها مؤكدة بالتحقق المستقل**: 4 حرجة، 10 متوسطة، و16 تحسينًا.
2. أخطر ما وُجد على الصلاحيات في **lib/api.js** (BE-1 وBE-2): مسار الأدوار القديم في `createUser`/`updateUser` يسمح حرفيًا بتعيين `role='admin'` — أي صلاحية `'*'` الكاملة — متجاوزًا فحص التفويض `canDelegateProfile` لأي فاعل يملك `users:write`.
3. أخطر ما وُجد على البيانات في **render.yaml** (DB-1): قاعدة `data/laurette.db` بلا آلية نسخ احتياطي إطلاقًا؛ بلا قرص دائم تُمحى مع كل إعادة نشر، ومع القرص المعرَّف يطغى التثبيت على مجلد `data/` ويخفي `seed.json` المطلوب في الإقلاع.
4. ويقابله في **lib/db.js** (DB-2): هجرات إقلاع تلفية بـ `DROP TABLE requests` (وبالمثل `bookings`) بلا لقطة احتياطية قبلها، مع فقد فهارس الجدول الأربعة حتى إعادة التشغيل التالية.
5. من المتوسطات: تزييف `X-Forwarded-For` في **lib/http.js** (BE-3) يفسد حدود المعدل وقفل الدخول وسجل التدقيق، خرائط `RateLimiter` بلا سقف للذاكرة (BE-4)، مسح جداول المحتوى وتفقد تعديلات لوحة الإدارة عند تغيّر `seed_version` (DB-3 في **lib/db.js**)، وفشل `SQLITE_BUSY` الفوري لغياب `busy_timeout` (DB-4).
6. اختبار الإقلاع الحي **نجح بلا أخطاء** (استجابات 200 للصفحات و401 للحماية على `/api/admin/reports`، وسجل أخطاء فارغ)، لكنه أكد كتابات إقلاع على القاعدة قبل فتح المنفذ (server.js:74 — SM-1) وظهور ملفي `-wal`/`-shm` على أصل القاعدة خارج مسار التشغيل (SM-2).
7. **2 من 5 فاحصين لم يعيدوا نتائج** (فجوة موثقة في قسم حدود الفحص)، وملف ملاحظات الواجهة الأمامية (`frontend-findings.json` — FE-1..FE-11) خرج عن مصادر هذا التقرير المحددة ولا يشمله التحقق المستقل؛ أُثبتت عناوينه في ملحق بحاجة مراجعة بشرية.
8. خطة إصلاح الملاحظات الحرجة للملفات الثلاثة (**lib/api.js**، **lib/db.js**، **render.yaml**) مفصلة في القسم 6 وهي معروضة للموافقة قبل أي تطبيق.

```js
export function openDb(file) {
  if (file !== ':memory:') mkdirSync(dirname(file), { recursive: true });
  const db = new DatabaseSync(file);
  db.exec(SCHEMA);
  const requestSchema = one(db, "SELECT sql FROM sqlite_master WHERE type = 'table' AND name = 'requests'")?.sql || '';
  if (!requestSchema.includes("'cruise'")) {
    const newRequestSchema = SCHEMA.match(/CREATE TABLE IF NOT EXISTS requests \([\s\S]*?\n\);/)?.[0]
      ?.replace('CREATE TABLE IF NOT EXISTS requests', 'CREATE TABLE requests_new');
    if (!newRequestSchema) throw new Error('Unable to build the additive requests table migration');
    db.exec('PRAGMA foreign_keys = OFF');
    try {
      db.exec('BEGIN IMMEDIATE');
      db.exec('DROP TABLE IF EXISTS requests_new');
      db.exec(newRequestSchema);
      const oldColumns = db.prepare('PRAGMA table_info(requests)').all().map((column) => column.name);
      const newColumns = db.prepare('PRAGMA table_info(requests_new)').all().map((column) => column.name);
      const copyColumns = oldColumns.filter((column) => newColumns.includes(column));
      const names = copyColumns.map((column) => `"${column}"`).join(', ');
      db.exec(`INSERT INTO requests_new (${names}) SELECT ${names} FROM requests`);
      db.exec('DROP TABLE requests');
      db.exec('ALTER TABLE requests_new RENAME TO requests');
```

- **الأثر:** خطر مباشر على البيانات الحية عند كل ترقية من مخطط قديم (تعطل منتصف الهجرة يتراجع بالمعاملة، لكن فشلًا منطقيًا بعد COMMIT لا تراجع له ولا لقطة للعودة)؛ وعلى أول إقلاع بعد هجرة requests تعمل الاستعلامات بلا الفهارس الأربعة (مسح كامل) حتى النشر التالي.
- **الإصلاح المقترح:** أخذ لقطة إلزامية قبل أي هجرة DROP-based (VACUUM INTO أو نسخ الملف) مع retention قصير، وإعادة إنشاء كل فهارس الجدول داخل المعاملة نفسها بعد RENAME، واختبار الهجرات على لقطة من قاعدة الإنتاج الفعلية.
- **التحقق المستقل:** ✅ **مؤكدة** — ملاحظة المدقق: «أعدت إثباته من الكود. lib/db.js:538 فعلاً `db.exec('DROP TABLE requests')` داخل هجرة محمية بشرط غياب 'cruise' في sqlite_master (:524) وBEGIN IMMEDIATE (:530) وDROP TABLE IF EXISTS requests_new (:531)» (مقطوعة في السجل كما وردت). قراءتي المباشرة أكدت الأسطر 519-539 بالكامل بما فيها السطر 538 حرفيًا.

## 6) خطة إصلاح الأخطاء الحرجة (معروضة للموافقة قبل التطبيق)

جمعت الملاحظات الحرجة المؤكدة الأربع حسب ملفها. **هذه الخطة وصف للتعديلات المقترحة فقط — لم يُعدَّل أي ملف، والتطبيق لا يتم إلا بعد موافقة المالك.**

### 6.1 ملف lib/api.js — الملاحظتان BE-1 وBE-2 (كسر التحكم بالوصول في تعيين الأدوار)

**الفكرة الجامعة:** لا يجوز اشتقاق دور `admin` — أو أي دور — من مدخلات الطالب إلا عبر مسار واحد محكم؛ يجب أن يخضع «المسار القديم» (role بلا role_key) لنفس فحوص مسار `role_definitions` (canDelegateProfile + نطاق الفاعل)، وأن يُمنع تغيير دور الحساب الذاتي في المسارين.

التعديلات المطلوبة بالترتيب:

1. **في `createUser` (الأسطر 1407-1448):**
   - عند إرسال `roleKey` فارغًا مع `body.role` بقيمة `admin` (أو أي دور يجعل `resolvedRole` يأتي مباشرة من body عبر السطر 1424 `const resolvedRole = profile ? profile.base_role : role;`): اشتراط أن يكون الفاعل مديرًا قديمًا (`user.role === 'admin' && !user.roleKey`) وإلا رفض 403 برسالة عربية واضحة.
   - إضافة فحص الدور قبل حراس النطاق الحاليين (1435-1437) لأنهم يفحصون الفرع/القسم فقط ولا يفحصون الدور.
2. **في `updateUser` (الأسطر 1450 وما بعدها):**
   - فرع role القديم (1476-1480): تطبيق `canDelegateProfile` وفحص نطاق الفاعل عليه كما في فرع roleKey (1463-1475)، وحظر `role='admin'` عبر هذا المسار لغير المدير القديم.
   - تصحيح شرط الحساب الذاتي عند 1477: الشرح الحالي `target.id === user.id && body.role !== 'admin'` يمنع الخفض فقط ويسمح حرفيًا بتعيين admin على الذات — المطلوب منع أي تغيير لدور الحساب الذاتي في المسارين (422 دائمًا عند `target.id === user.id` مع تعديل دور).
3. **اختبارات مرافقة (ثلاث حالات على الأقل):** فاعل يملك `users:write` بدور مقيد يحاول إنشاء/ترقية admin عبر المسارين → 403؛ مدير قديم يمنح admin → نجاح؛ أي مستخدم يغيّر دوره الذاتي في المسارين → 422.

### 6.2 ملف lib/db.js — الملاحظة DB-2 (هجرات إقلاع تلفية بلا لقطة)

**الفكرة الجامعة:** أي هجرة تحذف جدولًا (`DROP TABLE`) يجب ألا تعمل أبدًا دون لقطة قابلة للاستعادة، وعلى استعادة فهارس الجدول في المعاملة نفسها.

التعديلات المطلوبة بالترتيب:

1. **لقطة إلزامية قبل الهجرة:** قبل `BEGIN IMMEDIATE` في كتلة هجرة requests داخل `openDb` (السطر 530): تنفيذ `VACUUM INTO` إلى ملف مثل `data/backups/pre-migration-<timestamp>.db` مع سياسة retention بسيطة (الاحتفاظ بآخر 3 لقطات وحذف الأقدم). نفس الشرط يطبق على هجرة bookings في `lib/workspace-db.js` المذكورة في سجل الملاحظة.
2. **استعادة الفهارس داخل المعاملة:** بعد `ALTER TABLE requests_new RENAME TO requests` (السطر 539) داخل المعاملة نفسها، إعادة إنشاء الفهارس الأربعة idx_requests_status/type/created/customer — حاليًا تسقط مع الجدول القديم ولا يُعاد جزء منها إلا في إقلاع لاحق (يغطي الـ backfill الحالي client/deal/org/intake فقط).
3. **اختبار قبل النشر:** تشغيل الهجرة على لقطة من قاعدة إنتاج حقيقية قبل أي نشر؛ المعاملة تتراجع عند التعطل منتصف التنفيذ فقط، أما الفشل المنطقي بعد COMMIT فلا تراجع له ولا لقطة للعودة (كما في سجل الملاحظة).

### 6.3 ملف render.yaml — الملاحظة DB-1 (فقد القاعدة على Render)

**الفكرة الجامعة:** فصل القرص عن مجلد المصدر، ونسخ احتياطي خارجي، وإغلاق نظيف عند النشر.

⚠️ **قرار مسبق مطلوب من المالك:** تغيير `mountPath` يعيد تعريف مكان بيانات النشر — قبل التطبيق يلزم اختيار أحد المسارين: (أ) البقاء على SQLite مع خطة تدعم القرص الدائم وتصحيح نقطة التثبيت كما في البنود أدناه، أو (ب) الانتقال لقاعدة مُدارة. هذا قرار نشر/تكلفة لا يُتخذ تلقائيًا.

التعديلات المطلوبة بالترتيب (عند اعتماد المسار أ):

1. **نقل القرص خارج مجلد المصدر:** في render.yaml تغيير `mountPath` من `/opt/render/project/src/data` إلى مسار مستقل مثل `/var/data`، وإضافة متغير بيئة `DB_FILE=/var/data/laurette.db` إلى `envVars` — server.js:67 يقرأ `DB_FILE` أصلًا فلا يلزم تعديل شيفرة لهذه الخطوة. بذلك لا يطغى التثبيت على `seed.json` الذي يبقى في مجلد المصدر (`data/seed.json` في المستودع) ولا تُخفى ملفات المستودع خلف نقطة التثبيت.
2. **نسخ احتياطي دوري:** سكربت نسخ احتياطي (بأمر `sqlite3 ... ".backup"` أو `VACUUM INTO`) يعمل مجدولًا ويرفع النسخة لمخزن خارجي — جرد `tools/` الحالي لا يضم أي سكربت نسخ احتياطي (من سجل الملاحظة)، وهذا شرط لا بديل عنه طالما القاعدة على قرص.
3. **إغلاق نظيف:** إضافة معالج `SIGTERM` في server.js يستدعي `app.close()` (يغلق اتصال القاعدة المفتوح في server.js:485) — Render يرسل SIGTERM عند كل نشر والخادم حاليًا لا يعالجه (من سجل الملاحظة)، والإغلاق النظيف يقلل خطر تلف WAL عند النشر.
4. **توثيق:** تدوين في README أن الخطة المجانية بلا قرص دائم (كما يقول تعليق render.yaml نفسه في الأسطر 2-3) وأن البيانات تُمحى مع كل نشر دون البنود أعلاه.
