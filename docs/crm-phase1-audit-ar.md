# المرحلة الأولى — تدقيق النظام الحالي ومخطط CRM التشغيلي

**الشركة:** Laurette Travel & Tourism
**المشروع:** Enterprise CRM & Multi-Branch Operations
**نوع المستند:** مخرج المرحلة 1 (تدقيق + مخطط) — **لا يتضمن تنفيذًا بعد**
**التاريخ:** 27 أكتوبر 2026
**المرجع:** الأمر الإداري والتقني لإعادة هيكلة نظام CRM (18 قسمًا)

---

## 1. الملخص التنفيذي

1. **النظام الحالي ليس CRM تشغيليًا**، بل منصة موقع + استقبال طلبات: 26 جدولًا، منها 20 للمحتوى (برامج، وجهات، عروض، مقالات…)، وجدولان فقط للعمل (requests, customers).
2. **الهيكل التنظيمي غائب تمامًا:** لا جداول `branches` أو `departments` أو `employees`؛ «القسم» و«الفرع» نصوص حرة داخل الطلب والمستخدم.
3. **الصلاحيات الحالية ثلاثة أدوار فقط** (`admin`, `manager`, `agent`) وقائمة إجراءات ثابتة في الكود، بلا نطاق فرع/قسم/سجل، وبلا أدوار المالية والتدقيق.
4. **دورة الحياة سبع حالات** في حقل واحد `requests.status`، مدمجة مع `deal_status` المشتق؛ الأمر يطلب 17 حالة مع فصل مرحلة الفرصة عن التنفيذ عن الدفع.
5. **الوحدات الغائبة كليًا:** التحويلات وقبولها، SLA والتصعيد، العروض المتعددة وتكلفة المورد والهامش، الدفعات، الموردون، المهام، الإشعارات، أسباب الخسارة، لوحات الفرع/القسم/الإدارة، سجل تدقيق بفروق قبل/بعد.
6. **الخبر الجيد:** الأساس التقني سليم وقابل للتوسعة — SQLite عبر `node:sqlite`، خادم HTTP بلا اعتماديات، مصادقة جلسات، `audit_log` أولي، 72 مسارًا، و66 اختبارًا تمر. لا حاجة لإعادة كتابة الموقع، بل **توسعة إضافية (Additive)** على نفس القاعدة.

**القرار المعماري المقترح:** توسعة تدريجية على القاعدة الحالية، بإضافة جداول وأعمدة جديدة وترحيل آمن، مع إبقاء كل الوظائف والتصميم الحاليين كما هما.

## 2. الوضع الحالي بالأرقام (مقروء من الكود وقاعدة `data/laurette.db`)

| المؤشر | القيمة |
|---|---|
| جداول قاعدة البيانات | 26 |
| جداول المحتوى | 20 (programs 75، destinations 36، offers 17، articles 6، faq 14، hotels 16، airlines 12، news 5، reviews 5، visa 6، trip ideas 10، kb 18 …) |
| جداول العمل | `customers` (1)، `requests` (1)، `request_events` (3)، `audit_log` (26) |
| المستخدمون | 1 (`laurette`، دور `admin`) |
| مسارات الخادم | 72 مسارًا (صفحات + API + إدارة) |
| معالجات API | 33 دالة في `lib/api.js` |
| الأدوار | 3: `admin`, `manager`, `agent` |
| حالات الطلب | 7: `new, reviewing, quoted, awaiting, in_progress, confirmed, cancelled` |
| مراحل الصفقة | 4 مشتقة: `new, in_progress, won, lost` |
| الاختبارات | 66 اختبارًا (API + لغتان + قسيمة) |

### 2.1 ما الذي يعمل اليوم فعليًا

- استقبال طلب من الموقع بستة أنواع (طيران، فندق، برنامج، عمرة، تأشيرة، استشارة) برقم مرجعي فريد.
- تحقق خادمي كامل، منع تكرار خلال 15 دقيقة، وإنشاء/دمج ملف عميل بالهاتف.
- لوحة إدارة: طلبات، عملاء، برامج، محتوى، تأشيرات، موظفون، إعدادات، تقارير أداء أساسية.
- تغيير حالة الطلب مع منع الانتقالات غير المسموحة وسجل أحداث.
- عرض سعر واحد لكل طلب (`quote_amount`, `quote_note`) يظهر للعميل في `/track`.
- إسناد الطلب إلى موظف واحد (`assigned_to`).
- `audit_log` بسيط (من/ماذا/متى/IP) لتسجيل الدخول وتعديل الطلبات.
- متابعة العميل لطلبه بالرقم المرجعي + الهاتف.

### 2.2 ما الذي لا يعمل / غير موجود

- لا فروع ولا أقسام ككيانات، ولا ربط موظف بفرع/قسم/مدير.
- لا تحويل طلب بين موظف/قسم/فرع، ولا قبول/رفض تحويل، ولا ملكية مؤقتة.
- لا طلبات متعددة الأقسام (Parent/Sub).
- لا أولويات ولا تواريخ استحقاق ولا مرفقات.
- لا SLA ولا تنبيهات ولا تصعيد.
- لا عروض متعددة ولا تكلفة مورد ولا هامش ربح ولا صلاحية عرض.
- لا دفعات ولا موردين ولا أرباح فعلية.
- لا أسباب خسارة ولا إعادة فتح صفقة.
- لا لوحات فرع/قسم/إدارة عامة، ولا تقارير قابلة للتصدير Excel/PDF (CSV فقط).
- لا سجل تدقيق للقيم السابقة/الجديدة ولا سبب التعديل، ولا منع حذف.
- لا صلاحيات على مستوى السجل (كل `agent` يرى كل الطلبات).

## 4. نموذج البيانات المستهدف (توسعة إضافية)

> المسودة الكاملة غير المنفذة في `docs/crm-schema-draft.sql`. المبدأ: **إضافة فقط**، بلا حذف أو إعادة تسمية لأي جدول قائم.

### 4.1 الجداول الجديدة (19)

| الجدول | الغرض | مفاتيح/قيود أساسية |
|---|---|---|
| `branches` | إربد (رئيسي)، عمّان | `code UNIQUE`، `is_head_office` |
| `departments` | الأقسام التسعة | `code UNIQUE`، `branch_scope` |
| `branch_departments` | تفعيل قسم داخل فرع | PK مركّب `(branch_id, department_id)` |
| `employees` | ملف الموظف | `user_id UNIQUE`، `employee_no UNIQUE`، `branch_id`، `department_id`، `manager_id` |
| `roles` | 8 أدوار قابلة للتوسعة | `code UNIQUE` |
| `permissions` | قدرات دقيقة `requests.transfer` … | `code UNIQUE` |
| `role_permissions` | ربط الدور بالقدرة | PK `(role_id, permission_id)` |
| `user_roles` | أدوار متعددة للمستخدم + نطاق | `scope_type` (global/branch/department/self) |
| `request_transfers` | مركز التحويل | `status` (pending/accepted/rejected), `from_*`, `to_*`, `reason`, `decided_at` |
| `request_assignments` | تاريخ الإسناد والملكية | `is_current` (فهرس فريد جزئي) |
| `request_subrequests` | طلب رئيسي ← مهام أقسام | `parent_id`, `child_id` أو `request_id` + `department_id` |
| `request_tasks` | مهام التنفيذ داخل الطلب | `status`, `due_at`, `assigned_to` |
| `request_status_history` | كل تغيير حالة مع before/after | `from_status`, `to_status`, `actor_id`, `reason` |
| `suppliers` | موردون (طيران/فنادق/تأشيرات) | `type`, `name` |
| `quotations` | نسخ عرض متعددة | `version`, `status`, `valid_until`, `cost_total`, `sell_total` |
| `quotation_items` | بنود العرض | `quotation_id`, `kind`, `cost`, `price` |
| `payments` | دفعات/استرداد | `direction`, `method`, `amount`, `reference` |
| `lost_reasons` | أسباب الخسارة | `code`، قابلة للتوسعة من الإدارة |
| `follow_ups` | مهام متابعة | `due_at`, `done_at`, `owner_id` |
| `notifications` | إشعارات داخلية | `user_id`, `read_at`, `entity` |
| `sla_policies` | مدد الاستجابة/التصعيد | `department_id`, `priority`, `first_response_min`, `resolve_min` |
| `business_hours` | ساعات العمل لكل فرع | `branch_id`, `weekday`, `from`, `to` |
| `audit_logs` (جديد) | تدقيق كامل | `before_json`, `after_json`, `reason`, `actor_id`, `entity`, `entity_id`, `created_at` (بلا UPDATE/DELETE من التطبيق) |

### 4.2 أعمدة تُضاف إلى `requests` (بدون حذف أي عمود)

`branch_id`, `department_id`, `owner_id` (الموظف المسؤول الحالي), `priority`, `due_at`, `received_at`, `source_code`, `customer_type`, `service_code`, `opportunity_stage`, `execution_stage`, `payment_status`, `lost_reason_id`, `closed_at`, `reopened_at`, `parent_request_id`.

> تبقى الأعمدة القديمة (`status`, `deal_status`, `department`, `assigned_to`) للتوافق الخلفي، وتُملأ الجديدة منها أثناء الترحيل، ثم تصبح القديمة مشتقة/للقراءة فقط.

### 4.3 فهارس وقيود حاكمة

- `requests(reference)` UNIQUE (قائم)، `requests(branch_id, status)`, `requests(owner_id, due_at)`, `requests(department_id, updated_at)`.
- `request_transfers(request_id, status)` + فهرس فريد جزئي: تحويل واحد `pending` لكل طلب.
- `request_assignments` فهرس فريد جزئي `WHERE is_current = 1` لضمان **مالك واحد فقط**.
- `quotations(request_id, version)` UNIQUE.
- `payments(request_id, created_at)`.
- `audit_logs(entity, entity_id, created_at)`.
- قيود `CHECK` على الحالات والمبالغ غير السالبة.

## 5. الصلاحيات: من 3 أدوار إلى 8 + نطاق

### 5.1 الأدوار المطلوبة

`super_admin` · `general_manager` · `branch_manager` · `department_manager` · `team_leader` · `employee` · `finance` · `auditor`

### 5.2 نموذج التطبيق

1. **قدرات دقيقة** في جدول `permissions` (مثال: `requests.read`, `requests.assign`, `requests.transfer`, `requests.change_status`, `quotations.read_cost`, `payments.record`, `reports.export`, `audit.read`).
2. **دور ← قدرات** في `role_permissions` (قابلة للتعديل من الإدارة، لا في الكود).
3. **نطاق** لكل إسناد دور في `user_roles.scope_type` + `scope_id`:
   - `global`: كل الفروع (المدير العام، المالية، التدقيق).
   - `branch`: فرع واحد.
   - `department`: قسم داخل فرع.
   - `self`: طلباته فقط (الموظف).
4. **الحكم على الخادم**: كل معالج API يمرّ بـ`requirePermission(user, 'requests.transfer', { requestId })` التي تتحقق من القدرة **ومن النطاق على السجل**، ثم تُسجّل المحاولة المرفوضة في التدقيق.
5. **إخفاء الحقول المالية**: `quotations.read_cost` و`reports.profit` منفصلتان؛ من لا يملكهما لا تُرسل إليه التكلفة/الهامش في JSON أصلًا (لا إخفاء واجهة فقط).

## 6. دورة حياة الطلب: 17 حالة بثلاث طبقات

بدل حقل واحد، ثلاثة حقول مستقلة تمنع «اعتبار الصفقة مكتملة بمجرد موافقة العميل»:

| الطبقة | الحقل | القيم |
|---|---|---|
| الفرصة البيعية | `opportunity_stage` | new_lead, unassigned, assigned, pending_acceptance, in_progress, quotation_preparation, quotation_sent, follow_up, negotiation, customer_confirmed, lost, on_hold |
| التنفيذ | `execution_stage` | not_started, payment_pending, booking_in_progress, confirmed_issued, completed, cancelled |
| الدفع | `payment_status` | unpaid, partial, paid, refunded |

### 6.1 حرّاس الانتقال (أمثلة ملزمة)

- `quotation_sent` تتطلب وجود `quotation` بحالة `sent` وصلاحية غير منتهية.
- `customer_confirmed` تتطلب موافقة مسجّلة (من/متى) ولا تنقل التنفيذ تلقائيًا.
- `booking_in_progress` تتطلب `payment_status != unpaid` أو موافقة مالية صريحة.
- `confirmed_issued` تتطلب `execution_stage=booking_in_progress` + تأكيد مورد/تذكرة.
- `completed` تتطلب `payment_status=paid` (أو تسوية مالية مسجلة) + كل المهام مغلقة.
- `lost` تتطلب `lost_reason_id` وقيمة متوقعة.
- `on_hold` تتطلب سببًا وتاريخ مراجعة.

### 6.2 الجدولة

جدول `status_transitions` (أو ثابت في `domain.js`) يحدد: من، إلى، القدرة المطلوبة، الشروط، ومن يُشعر. أي محاولة غير مسموحة تُرفض 422 وتُسجّل.

## 7. مركز التحويل (Request Transfer & Assignment Center)

### 7.1 الحقول

`request_id`, `from_branch/department/user`, `to_branch/department/user` (أو `to_department` للتوزيع), `reason`, `note`, `status` (pending/accepted/rejected/returned), `decided_by`, `decided_at`, `rejection_reason`, `created_at`.

### 7.2 قواعد إلزامية

1. **ذرّية**: التحويل + تغيير الملكية + الحدث + الإشعار داخل معاملة واحدة (`BEGIN IMMEDIATE … COMMIT`).
2. **مالك واحد دائمًا**: أثناء `pending` يبقى `owner_id` السابق مالكًا مسؤولًا، ويُضاف `pending_owner_id` للجهة المستلمة؛ لا يُترك الطلب بلا مالك.
3. **قبول**: ينتقل `owner_id` إلى المستلم، ويُغلق الإسناد السابق (`is_current=0`) ويُفتح جديد.
4. **رفض**: يُسجّل السبب، ويعود الطلب للمالك السابق أو لقائمة توزيع القسم بحسب `sla_policies`/سياسة التوزيع.
5. **منع الحلقات**: حد أقصى (مقترح 3 تحويلات خلال 7 أيام لنفس الطلب) ثم يتطلب موافقة مدير + إشعار.
6. **الطلبات المركّبة**: `parent_request_id` + مهام لكل قسم، ومالك واحد للطلب الأم يبقى مسؤولًا أمام العميل.
7. **الإشعار**: `notifications` + عدّاد في الواجهة؛ الإشعار لا يُعد إجراءً.

## 8. SLA والمتابعة

- `sla_policies(department_id, priority, first_response_min, quotation_min, follow_up_min, resolve_min, escalate_to_role)`.
- حساب الزمن على **ساعات العمل** (`business_hours`) لكل فرع، مع استثناء الجمعة/السبت أو حسب السياسة.
- مؤقت يومي (مهمة مجدولة كل 15 دقيقة) يفحص:
  - طلب جديد بلا استلام،
  - تحويل `pending` تجاوز المدة،
  - عرض سعر لم يُرسل،
  - متابعة مستحقة اليوم،
  - عرض قارب الانتهاء،
  - طلب بلا تحديث.
- التصعيد: موظف ← مدير قسم ← مدير فرع ← مدير عام، بحسب العتبات، مع منع التكرار (إشعار واحد لكل عتبة).

## 9. العروض والمالية

- `quotations` بنسخ (`version`) وحالة (`draft/sent/accepted/rejected/expired`) وصلاحية `valid_until`، و`created_by`.
- `quotation_items`: بند، مورد، تكلفة، سعر بيع، عملة، هامش محسوب.
- **الربح المتوقع** = Σ(بيع − تكلفة) للنسخة المقبولة؛ **الربح الفعلي** = المدفوع − التكلفة الفعلية − الاستردادات + التسويات.
- `payments`: دفعة/استرداد، طريقة، مرجع، مرفق، من سجّلها ومن اعتمدها.
- رؤية التكلفة والهامش محصورة بـ`quotations.read_cost` (Super/GM/Finance/Auditor) ولا تُرسل لغيرهم.
- عند `customer_confirmed`: تُنشأ `booking` (أو `execution`) مرتبطة بالعرض مع الحفاظ على سجل المبيعات.

## 10. لوحات التحكم والتقارير — خريطة التنفيذ

| اللوحة | المصدر الأساسي | مؤشرات رئيسية |
|---|---|---|
| الموظف | `requests` (owner=self) + `follow_ups` + `notifications` | طلباتي الجديدة، بانتظار قبول، قيد العمل، عروض مرسلة، متابعات اليوم، متأخرة، محوّلة مني/إليّ، مكتملة/خاسرة |

## 11. سجل التدقيق

- جدول `audit_logs` جديد (لا يُستبدل `audit_log` القديم): `entity`, `entity_id`, `action`, `before_json`, `after_json`, `reason`, `actor_id`, `ip`, `created_at`.

## 12. خطة الترحيل الآمنة (Additive)

1. **نسخة احتياطية** من `data/laurette.db` + `-wal` قبل أي شيء.
2. تطبيق DDL الجديد فقط (جداول + أعمدة `NULL`).
3. زرع البيانات المرجعية: فرعان، 9 أقسام، 8 أدوار، قدرات، `sla_policies` افتراضية.
4. ترحيل المستخدم الحالي: `admin` ← `super_admin` + `employees` برقم وظيفي مؤقت وفرع إربد.
5. Backfill للطلبات الحالية: `branch_id`=إربد، `department_id` من `requests.department`، `owner_id`=`assigned_to`، `opportunity_stage` من `status`، `execution_stage` من `deal_status`، `payment_status=unpaid`.
6. الإبقاء على الأعمدة القديمة متزامنة (Trigger أو كود) لحين اعتماد الواجهات الجديدة.
7. تشغيل 66 اختبارًا + اختبارات جديدة للترحيل، ومقارنة عدد الصفوف قبل/بعد.
8. Rollback: حذف الجداول الجديدة وإرجاع النسخة الاحتياطية (لا تُلمس الجداول القديمة أثناء المرحلة).
