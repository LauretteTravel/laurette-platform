# تتبع الصفقات والتقارير وربط الحملات الإعلانية

دليل عملي لتشغيل المزايا المضافة على منصة لوريت. كل شيء يعمل محليًا؛ لا تحتاج أي حزمة أو مكتبة جديدة.

---

## 1) التثبيت والترحيل (تلقائي)

شغّل الخادم كالمعتاد:

```bash
cd laurette-platform
node server.js
```

عند الإقلاع ينفّذ `lib/db.js` ترحيلًا خفيفًا بأمان:

| العملية | التفصيل |
|---|---|
| `ALTER TABLE requests ADD deal_status` | مرحلة الصفقة (`new` / `in_progress` / `won` / `lost`) |
| `ADD completed_at` | وقت إغلاق الصفقة (ناجحة أو ملغية) |
| `ADD first_response_at` | وقت أول إجراء من الموظف (حالة/إسناد/عرض/ملاحظة) |
| `CREATE INDEX idx_requests_deal` | تسريع تقارير الصفقات |
| `CREATE TABLE tracking_events` | سجل مجهول لأحداث التحويل (بلا بيانات شخصية) |
| Backfill | تحويل الطلبات القديمة إلى المرحلة المناسبة تلقائيًا |

لا حاجة لأمر ترحيل يدوي، ولا تُفقد أي بيانات موجودة.

### خريطة الحالة → مرحلة الصفقة

| حالة الطلب | مرحلة الصفقة | وقت الإغلاق |
|---|---|---|
| `new` | `new` جديد | — |
| `reviewing` / `quoted` / `awaiting` | `in_progress` قيد المتابعة | — |
| `confirmed` | `won` مكتملة/ناجحة | يُسجَّل تلقائيًا |
| `cancelled` | `lost` ملغية | يُسجَّل تلقائيًا |

> الانتقالات نفسها محمية كما قبل (`new → reviewing → quoted → awaiting → confirmed`)، وأي انتقال غير مسموح يرجع `422`.

## 2) استخدام التقارير

من لوحة الإدارة: **تقارير الأداء**.

- أزرار **يومي / أسبوعي / شهري**، أو نطاق مخصص (تاريخ البداية والنهاية).
- فلترة بالموظف أو «غير مسند».
- المؤشرات: إجمالي الطلبات، الصفقات الناجحة/الملغية/المفتوحة، نسبة التحويل، معدل الفوز، متوسط زمن الإنجاز، متوسط أول استجابة، قيمة الصفقات الناجحة (من `quote_amount`).
- جداول: أداء كل موظف، التحويل حسب الخدمة، قمع الحالات.
- رسم زمني: إجمالي الطلبات مقابل الصفقات الناجحة.
- **تصدير CSV** لجدول الموظفين (يفتح في Excel مع BOM عربي).

### عبر الـAPI

```bash
# دخول
curl -c cookies.txt -X POST http://127.0.0.1:3000/api/auth/login \
  -H 'content-type: application/json' -H 'x-requested-with: fetch' \
  -d '{"username":"laurette","password":"..."}'

# تقرير أسبوعي
curl -b cookies.txt "http://127.0.0.1:3000/api/admin/reports?period=weekly"

# نطاق مخصص + موظف
curl -b cookies.txt "http://127.0.0.1:3000/api/admin/reports?period=monthly&from=2026-10-01&to=2026-10-31&employee=1"

# تصدير CSV
curl -b cookies.txt -o report.csv "http://127.0.0.1:3000/api/admin/reports.csv?period=weekly"
```

الصلاحية المطلوبة: `reports:read` (المدير ومدير القسم). الموظف العادي يحصل على `403`.
المدة تُحسب بالدقائق في الـAPI، وتُعرض بالعربية (دقيقة/ساعة/يوم) في الواجهة.

## 3) ربط Meta Pixel وGoogle

### الخطوات

1. ادخل `/admin` ← **التسويق والتتبع**.
2. الصق المعرفات:
   - **Meta Pixel ID**: من Meta Events Manager (رقم مثل `123456789012345`).
   - **GTM ID**: مثل `GTM-XXXXXXX` (اختياري لكنه مفيد لإدارة الوسوم).
   - **Google Ads Conversion ID**: مثل `AW-123456789`.
   - **Conversion Label**: من صفحة الحدث في Google Ads (اختياري).
3. اضغط «حفظ إعدادات التتبع».
4. افتح الموقع العام في نافذة جديدة، وأرسل طلبًا تجريبيًا، ثم راقب:
   - Meta Events Manager ← حدث `Lead` (و`SubmitApplication`).
   - GTM Preview / Tag Assistant ← `generate_lead`.
   - Google Ads ← التحويل بعد ربط التسمية.
5. اضغط زر واتساب واختر رقم فرع ← حدث `Contact` و`whatsapp_click`.

### ماذا يُحقن فعليًا؟

- سكربت تهيئة صغير في `<head>` بnonce، لا يتصل بأي نطاق خارجي حتى اكتمال تحميل الصفحة.
- بعد `load` + `requestIdleCallback` (بحد أقصى 2.5 ثانية): تحميل `gtm.js` و/أو `gtag.js` و/أو `fbevents.js` بشكل `async`.
- `noscript` لـGTM وكود تتبع Meta كصورة.
- عند نجاح الطلب، يُطلق المتصفح حدثًا داخليًا `loret:lead`، ويحوّله السكربت إلى:
  - `dataLayer.push({event:'generate_lead', lead_type, value, currency:'JOD'})`
  - `fbq('track','Lead', …)` + `fbq('trackCustom','SubmitApplication', …)`
  - `gtag('event','conversion',{send_to:'AW-…/LABEL', value})`
- عند اختيار رقم واتساب: `Contact` و`whatsapp_click` و`beacon` للسجل المحلي.

### الأداء والحماية

- لا يوجد أي طلب خارجي قبل `load`، ولا حجب للرسم (`async` فقط، بلا `sync` أو CSS خارجي).
- CSP تتوسع تلقائيًا لنطاقات Meta/Google فقط عند إدخال معرف؛ بلا معرفات تبقى السياسة ضيقة ولا يُحقن شيء.
- `Do Not Track` يوقف التتبع بالكامل.
- لا تُرسل أسماء أو هواتف أو مراجع طلبات إلى المنصات؛ فقط نوع الخدمة والقيمة التقريبية.
- الأحداث تُسجَّل محليًا في `tracking_events` (حدث، نوع، مسار، وقت) لمراجعتها من نفس القسم.

### إيقاف التتبع

- إفراغ المعرفات، أو إلغاء «تفعيل تتبع الحملات»، ثم الحفظ. يختفي السكربت من كل الصفحات فورًا.

## 4) التحقق السريع (سطر أوامر)

```bash
# هل السكربت موجود في الرأس؟
curl -s http://127.0.0.1:3000/ | grep -o "fbevents.js\|gtm.js\|gtag/js" | sort -u

# هل CSP يسمح بالنطاقات؟
curl -sI http://127.0.0.1:3000/ | grep -i content-security-policy

# أحداث مسجلة
curl -b cookies.txt http://127.0.0.1:3000/api/admin/tracking-events
```

## 5) استكشاف الأخطاء

| العَرَض | السبب المحتمل | الحل |
|---|---|---|
| لا تظهر أحداث Meta | معرف خاطئ أو مانع إعلانات | جرّب نافذة خاصة بلا مانع، وتأكد من Pixel ID |
| GTM لا يسجل | لم يُضف الحاوية أو تحظرها إضافة | افتح Preview، وتأكد من `GTM-…` |
| زر واتساب لا يرسل Contact | الحدث يُطلق عند اختيار الرقم لا عند فتح النافذة | اختبر بالضغط على رقم فرع |
| التقارير أصفار | لا طلبات في الفترة المحددة | وسّع النطاق أو أزل فلتر الموظف |
| «دخول غير صحيح» بعد نسخة جديدة | كلمة المرور تغيّرت | `node tools/reset-admin.mjs` |

## 6) ملاحظات صادقة

- التقارير مبنية على **وقت إنشاء الطلب**، لا على وقت أول تواصل؛ الطلبات التي أُنشئت قبل بداية الفترة لا تظهر فيها.
- «قيمة الصفقة» تعتمد على `quote_amount` الذي يدخله الموظف؛ إن لم يُسجَّل عرض سعر تبقى القيمة صفرًا.
- «أول استجابة» تُسجَّل عند أول إجراء موظف (تغيير حالة/إسناد/عرض/ملاحظة)، وليس عند فتح الطلب.
- لا يوجد تكامل Meta Conversions API من الخادم (Offline Conversions) ولا إسناد متعدد اللمسات (Multi-touch attribution)؛ هذه تحتاج حسابات ومفاتيح وتُعد تطويرًا لاحقًا.
- أرقام الاعتماد تُخزَّن في قاعدة SQLite محليًا؛ لا تُعرض في الواجهة العامة.
