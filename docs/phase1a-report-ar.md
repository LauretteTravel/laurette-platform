## ما أُنجز

| المشكلة | الإصلاح والتحقق |
|---|---|
| updateRequest محدود النطاق يرجع 500 | إضافة alias r للاستعلام؛ branch/department/assigned يحدثون طلبهم فعلًا، وخارج النطاق 404 دون كتابة |
| createRequestTransfer محدود النطاق يرجع 500 | alias r مع الاحتفاظ بفحص scope؛ تحويل مصرح به 201، وخارج النطاق 404؛ المالك يبقى كما هو قبل القبول |
| getCustomer محدود النطاق يرجع 500 | alias r في قائمة طلبات العميل؛ العميل المشترك لا يكشف الطلبات خارج النطاق |
| قبول/رفض تحويل من فرع غير مستهدف | يلزم الفرع المستهدف مع المستلم الصحيح/القسم المصرح أو مدير الفرع؛ حتى المستلم المسمى المنقول إلى فرع/قسم آخر يُرفض. المدير العام/legacy admin/manager يحافظون على صلاحياتهم التنظيمية الحالية |
| كشف سجل n8n العام | require settings:write ومستوى organization؛ مستخدم overview أو كاتب إعدادات branch لا يرى deliveries/target/summary/configured. لا إضافة لدور أو صلاحية جديدة في هذه المرحلة |
| غلاف api كان يكتفي بوجود الجلسة | بوابة مركزية withApiAuthorization تفحص الجلسة وmust_change وcan قبل المعالج، مع إبقاء requireUser في المعالجات دفاعًا إضافيًا |
| الموارد المولدة في حلقة لم تكن تمر بالغلاف | أخذ read/write من نفس RESOURCES policy، ولف كل موارد CRUD بالبوابة؛ manifest داخلي لاختبارات التغطية، غير متاح عبر HTTP |
| مؤشر جاهزية n8n لم يدعم Header Auth | الاستعانة بـwebhookConfig نفسها؛ دعم الرابط البديل وHMAC وN8N_WEBHOOK_KEY وN8N_API_KEY؛ عدم إرجاع المفتاح أو query string أو credentials؛ رابط مشوه لا يكسر صفحة الإدارة |

لم تتغير أحداث n8n أو التوقيع أو النقل أو جسم payload أو callback واتساب الموقّع. بقي CSRF كما هو، وتدفق تغيير كلمة المرور المؤقتة متاحًا، وبقيت صلاحيات الموارد الحالية كما هي؛ لم تُمنح صلاحيات إضافية من أجل إصلاح SQL.

## الملفات المعدلة

- `lib/api.js`: aliases للعمليات الثلاث، تفويض قرار التحويل، تقييد سجل التكامل وإعداده، مشاركة policy الموارد.
- `lib/api-authorization.js` (جديد): بوابة الموظفين المركزية المستقلة والقابلة للاختبار.
- `server.js`: ربط البوابة بـapi وبالموارد المولدة وتقييد مسار سجل n8n؛ manifest داخل createApp فقط.
- `lib/http.js`: describe للـrouter، يعيد metadata دون كشفه كمسار HTTP.
- `tests/phase1a.test.js` (جديد): 17 اختبارًا للانحدار والنطاق والتحويل والبوابة والمصفوفات.
- `Execution_Checklist.md`, `PR_DESCRIPTION.md`, هذا التقرير: حالة التسليم والحدود والمراجعة.

## قاعدة البيانات والنسخ والرجوع

**لا ترحيلات ولا تغييرات مخطط أو seed أو بيانات إنتاج.** اختبارات 1A في SQLite `:memory:` مصطنعة؛ الاختبارات القديمة ما زالت تستخدم قواعد اختبارها المعزولة.
نسخة المصدر قبل المرحلة: `data/pre-phase1a-882d5bb-source.zip`، مستثناة من Git، دون DB/.env أو بيانات عملاء؛ SHA256: `9D96B484803B45D3C6572D50397AFF959956D3F5F3BFC8B22ACBC2431257CEA2`.
الرجوع البرمجي، إذا لزم بعد اعتماد/نشر مستقبلي، عبر revert للالتزام التنفيذي في فرع مراجعة؛ لا استعادة DB مطلوبة لهذا التغيير. الرجوع يعيد العيوب السابقة لذلك يراجع أثره الأمني قبل تنفيذه. لا خطوات rollback نُفذت على الإنتاج.

- 1B: ترحيلات مرقمة ونسخ تلقائي، employees/memberships، MFA وحد12 وتدقيق before/after ومصفوفة إجراءات أوسع.
